# Coding Rules

- DOM処理は廃止し、reactの状態管理に極力任せること。
- 定数を利用し、マジックナンバーを使わないこと。
- 共通処理はまとめて、dry原則を保つこと。
- LocalStorageのユーザデータや、サーバ上のユーザデータとの不整合は絶対発生させないこと。（ユーザのデータの消失は最も注意すること）
- 【絶対厳守】変更・新規作成したすべてのファイルについて、インポート漏れや未定義の変数（no-undefなど）が絶対に発生していないか、コミットや報告の前に必ず `npm run format` や `eslint` を実行して二重チェック・検証すること。
  - **【先走りの絶対禁止】コード変更後は、必ず `npm run build` や `eslint` 等の検証ツールを実行し、その実行結果（エラーゼロ・100%成功）を自分の目で受信・確認するまで、決してユーザーへ「修正完了」などの報告テキストを先走って出力・送信してはならない。**
- 【絶対厳守】すべての関数へのドキュメント（JSDoc等）記載とシステム処理コメント記述の徹底
  - 新規作成・変更・追加するすべての関数（ヘルパー、コンポーネント、ユーティリティ問わず）に、その関数の概要・目的・引数（`@param`）・戻り値（`@return`）を明記したドキュメントコメント（JSDoc等）を**例外なく必ず記載すること**。
  - ゲームのシステムやバトルロジックに関わる処理は、人間が見て一目で挙動や目的が理解できるよう、具体的で丁寧な解説コメントを必ず記載すること。
- 【絶対厳守】オブジェクトプロパティ・関数戻り値の構造変更時における呼び出し元影響調査の徹底
  - 関数の戻り値やオブジェクトのプロパティを削除・置換・再構築する際、一部の局所的な差分や外部指摘（CodeRabbit等）のみに視野狭窄して作業してはならない。
  - **必ず事前に対象オブジェクト/関数の全呼び出し元を `grep` 検索で実地調査し、呼び出し側システム（対戦画面、モーダル、UI等）が要求しているプロパティ（例: `hp`, `playmat`, `color` 等）が欠落・消失しないことを100%検証してからコード変更に着手すること。**
  - セーブデータ（`savedConfig` 等）とマスタデータをマージする際は、セーブデータ由来の追加属性の消失を防ぐため既存オブジェクトをオブジェクトの先頭に展開し、計算・正規化済みのプロパティを後続で確実に上書き補正する設計順序を守ること。
- 【絶対厳守】報酬付与・カードドロップ・解放処理等の重要判定における「ホワイトリスト（許可制）方式」の徹底
  - ゲームモードや条件ごとの報酬付与、カードドロップ、機能解放などの判定を行う際、対象外を否定条件で列挙する「ブラックリスト（除外判定）方式（`mode !== 'a' && mode !== 'b' && ...`）」を**絶対に禁止する**。
  - 新モード追加時やすり抜け事故を恒久的に防ぐため、必ず「許可された対象のみを明示的に判定するホワイトリスト（許可制）関数（例: `checkIsCardDropEligible(gameMode)` 等）」を使用・定義すること。
- 【絶対厳守】AI思考・シミュレーションにおける「空きレーン優先・決め打ちヒューリスティック」の絶対禁止
  - AIの思考ルーチン、直前シミュレーション、シミュレーションエンジン（`engine.js`, `ai_normal.js` 等）において、「空きレーンがあればそこを優先する」「空きレーンがないから固定レーンを上書きする」といった**安直な空き枠優先ヒューリスティックや場当たり的な決め打ち・ハードコード（例: `const emptyLanes = ...; if (emptyLanes.length > 0) targetLane = emptyLanes[0]; else targetLane = validOccupiedLanes[0];`）を組み込むことを絶対に禁止する**。
  - トークン配置、使役、奇襲、分身、復活、傀儡、リーダースキル等、カードを場に置くあらゆるシミュレーションにおいて、「空きレーンへの配置」も「既存カード（味方カード・トークン・低パワーカード等）への上書き配置」も**等しく正当な候補レーン**として扱うこと。
  - シミュレーション内で配置先を決定する際は、手抜きで空きレーンに即決するのではなく、各候補レーンに配置した盤面の客観的な評価関数（`evaluateTurnOutcome` 等）スコアを正当に比較して最善手を選択すること。フォールバック時であっても、盤面状況を無視して固定レーンを破壊するのではなく、最弱カード・トークンの上書き等、合理的な選択ロジックを必ず用いること。
- 【絶対厳守】AIシミュレーション・評価における「上書きペナルティ（自壊ペナルティ）」の絶対禁止
  - AIの思考ルーチン、事前シミュレーション、直前シミュレーション（アドホックシミュレーション）等のあらゆる評価処理において、**「味方カードを上書きしたから減点する」「自壊させたからペナルティ（例: `score -= lostPower * 1000` 等）を与える」といった人為的・場当たり的な上書きペナルティ（自壊ペナルティ）の付与を完全に禁止する**。
  - このゲームのAI思考は、盤面にカードを配置・召喚した後の完全な戦闘シミュレーション（`advanceCombatPhase` 等）および客観的な盤面総合評価関数（`evaluateTurnOutcome` / `evaluateSimState`）によってのみ判断されなければならない。
  - 正しくシミュレーションを実行すれば、「空き枠に置けば盤面戦力が増加して敵リーダーへのダメージが増える」「強力な味方を上書きすれば盤面戦力が低下して敵リーダーへのダメージが減る」という結果が自然に計算され、評価関数スコアに正当に反映される。
  - 外部から小細工（ペナルティの減点、未来アクションを勝手に適用する `applyPendingDecisionActions` 等）を付け足すことは、シミュレーションの客観性を汚染・破壊し、正常なAI判断を妨げる有害なコードであるため、絶対に実装・追加してはならない。

# Game Rules

- デッキ枚数は20枚。
- LocalStorageにユーザデータを保存する。
- API経由でサーバに防衛戦のデッキやポイントを保存する。

## 【絶対厳守ルール】「召喚」と「配置」の厳密な区別

カードを場に出す処理を実装する際、以下の2種類のアクションを「絶対に」混同せず、分離して実装すること。

1. **「召喚（Summon）」**
   - **定義:** 手札からのプレイ、または制約ルール（伝説・生贄・挑戦・頂点）を満たしてカードを場に出すメインアクション。召喚時のオンプレイ能力が発動する。
   - **該当アクション・スキル一覧 (内部ID):**
     - **手札プレイ:** 手札からのカード通常召喚（メイン操作）
     - **「召喚」スキル:** `summon`（手札からの召喚、旧名: 詠唱 / `chant` を統合）
     - **「召集」スキル:** `assemble`（デッキからの召喚）
     - **「号令」スキル:** `call`（デッキトップからの召喚）
     - **「鍛造」スキル:** `forge`
     - **「狂気」スキル:** `madness`（手札から捨てられた時の召喚）
     - **リーダースキル「試練の宮殿」:** `dungeon_summon_leader`
   - **制約チェック:** **【あり（有効）】** (`checkConstraints = true`)
   - **実装基準:** レーン選択では `waitPlayerLaneSelection(..., checkConstraints = true)` を使用し、配置確定後に `resolveOnPlaySkill(...)` を呼び出して召喚時オンプレイ能力を発動する。
   - **挙動:** 「伝説（`legendary`: 中央のみ）」「生贄（`takeover`: 配置済みレーンのみ）」「挑戦（`challenge`: 正面に敵がいるレーン）」「頂点（`apex`: 自分場に伝説が必要）」などの配置制約ルールに**必ず従わなければならない**。
   - **画面ボタン表記:** 「召喚を完了」

2. **「配置（Place）」**
   - **定義:** スキル効果やリーダースキルによって、カードやトークンを制約ルールを無視して場に直接置く特殊アクション。原則として召喚時スキルは発動しない。
   - **該当アクション・スキル一覧 (内部ID):**
     - **「復活」スキル:** `resurrect`（自分の墓地からの配置）
     - **「傀儡」スキル:** `puppet`（相手の墓地からの配置）
     - **「分身」スキル:** `clone`（隣接レーンへの分身トークン配置）
     - **「使役」スキル:** `servant`（トークン配置）
     - **「奇襲」スキル:** `ambush`（トークン配置後に即攻撃）
     - **リーダースキル「竜王の降臨」:** `dragon_summon`
     - **リーダースキル「焦熱のプレリュード」:** `dragon_high_ritual`
     - **リーダースキル「魔王の化身」:** `satan_avatar`
     - **リーダースキル「聖なる進軍」:** `holy_march`
     - **リーダースキル「暗黒の軍勢」:** `evil_march`
     - **リーダースキル「棺の解放」:** `devilhunter_resurrect`
     - **リーダースキル「オーバードライブ」:** `overdrive`
     - **リーダースキル「魔宴の儀」:** `warlock_place_demons`
     - **リーダースキル「鉄の行進」:** `iron_march`
     - **リーダースキル「ラスト・バタリオン」:** `last_battalion`
     - **リーダースキル「百鬼夜行」:** `night_parade`
     - **リーダースキル「連携攻撃」:** `elf_polarbear_combo`
   - **制約チェック:** **【なし（無視）】** (`checkConstraints = false`)
   - **実装基準:** レーン選択では `waitPlayerLaneSelection(..., checkConstraints = false)` を使用し、`resolveOnPlaySkill(...)` を呼び出さない（オンプレイ能力を抑止する）。
   - **挙動:** 対象となるカードが「伝説」や「生贄」などの制約ルールを持っていたとしても、**封印レーンを除く任意のレーンに置くことができる**。
   - **画面ボタン表記:** 「配置を完了」

※ 重要例外: 「封印（`seal`）」されたレーンに関しては、レーン選択時（`waitPlayerLaneSelection`）と配置確定時（`playCard`）の両方の段階で、上記1および2のどちらの手段（召喚・配置）であっても**強制的に拒否・ブロックされ、配置することができない**。これは最優先のグローバルルールである。

## 【絶対厳守ルール】日本語スキル名の英語IDへの変換

ユーザーが日本語で指定した「スキル名」を、内部の英語IDに変換（または解釈）する際、**絶対に推測や類似の単語で代用せず、コード上の正確な対応表（src\utils\constants\skills.js）に基づいて厳密に一致させること**。

特に以下の取り違えはシステム破壊に直結する重大な違反とする：

- 「変身」＝ metamorph
- 「変化」＝ morph
- 「号令」＝ call
- 「狂気」＝ madness

ユーザーからスキルの修正や評価の指示があった場合は、必ず src\utils\constants\skills.js を確認し、日本語名（name）と英語キー（ID）の完全な対応関係を把握した上でコードの修正に着手すること。

## 【絶対厳守ルール】日本語リーダースキル名の英語IDへの変換

ユーザーが日本語で指定した「リーダースキル名」を、内部の英語ID（action）に変換する際、**絶対に推測や類似の単語で代用せず、コード上の正確な対応表（src\utils\constants\characters.js）の各キャラクターの `leaderSkill.action` に基づいて厳密に一致させること**。

- リーダースキルの英語IDは `CHARACTERS[key].leaderSkill.action`（例: `annihilation`, `devilhunter_resurrect`）である。
- 日本語名は `CHARACTERS[key].leaderSkill.name`（例: `殲滅光線`, `棺の解放`）である。
- リーダースキルは各キャラクターに紐づいているため、キャラクター名とリーダースキル名の両方を照合し、取り違えがないことを確認すること。
- ユーザーからリーダースキルの修正や指定の指示があった場合は、必ず src\utils\constants\characters.js を確認し、対象キャラクターの leaderSkill の name と action の完全な対応関係を把握した上でコードの修正に着手すること。

## 【絶対厳守ルール】日本語カード名の英語IDへの変換

ユーザーが日本語で指定した「カード名」を、内部の英語ID（id）に変換する際、**絶対に推測や類似の単語で代用せず、コード上の正確な対応表（src\utils\constants\cards.js）の `CARD_MASTER` 配列に基づいて厳密に一致させること**。

- カードの英語IDは各エントリの `id` プロパティ（例: `golem`, `clone`, `vampire`）である。
- 日本語名は各エントリの `name` プロパティ（例: `大理石のゴーレム`, `鏡の戦士`）である。
- カード名は似た名前が複数存在する場合があるため、**必ず完全一致で照合すること**。部分一致や推測による特定は禁止する。
- ユーザーからカードの修正や指定の指示があった場合は、必ず src\utils\constants\cards.js を確認し、日本語名（name）と英語ID（id）の完全な対応関係を把握した上でコードの修正に着手すること。
