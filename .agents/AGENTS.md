# Development Priorities & Canonical Sources

## 最優先原則（優先順位）

判断が競合した場合は、必ず以下の優先順位に従うこと。

1. **ゲーム仕様の正確性**
2. **ユーザーデータの保護と整合性**
3. **既存機能との後方互換性**
4. **バグの予防と回帰防止**
5. **コードの可読性・保守性**
6. **パフォーマンス**
7. **開発効率とAIレビューの効率**

## ゲーム仕様の正本ファイル

以下のマスタ定義を正本とし、**未確認の仕様・ID・挙動を推測で補完してはならない**。

- スキル定義: `src/utils/constants/skills.js`
- キャラクター定義: `src/utils/constants/characters.js`
- リーダースキル定義: `src/utils/constants/leaderSkills.js`
- カードマスタ定義: `src/utils/constants/cards.js`

# Development Workflow

- **実装前:** 正本マスタ・関連コード・既存テスト（`scripts/test_*.js`）を確認し、変更影響範囲（UI・モーダル・バトル・AI・セーブデータ・PHP API）を特定すること。複雑な変更では着手前に方針を明確にすること。
- **実装中:** 最小限の変更を優先し、無関係な変更や大規模リファクタリングを混在させないこと。未使用の外部ライブラリを追加する場合は事前にユーザーへ確認すること。ゲーム状態の不変条件・非同期安全性・データ互換性・JSDocを維持すること。
- **実装後:** 変更差分を確認し、関連テスト（`node scripts/test_*.js` 等）、Lint、ビルドを実行してセーブデータへの影響がないか検証すること。未実施の検証は推測せず「未実施」と明記し、変更内容・影響範囲・残存リスクを日本語で報告すること。

# Coding Rules

- **React状態管理・副作用・DOM操作**
  - DOM処理は廃止し、Reactの状態管理に極力任せること。React管理下UIの直接DOM書き換え（jQuery等を含む）は禁止し、バトル進行状態は `GameState`（`src/state/gameState.js`）と再描画通知フック（`updateBattleUIHook` 等）で同期すること。
  - ただし、`useRef` / `document.activeElement` によるフォーカス制御、要素サイズ・座標計測（VFX演出等）、オフスクリーン Canvas / Media 処理、ダウンロード用一時要素などの正当なブラウザAPI操作は区別して許容する。
  - React State・Propsの直接破壊的変更および描画中の副作用を禁止する。`useEffect` のタイマー・リスナー・フック登録はクリーンアップで確実に解除し、`<React.StrictMode>` 二重実行時の破綻や非同期内の古いState（stale closure）参照を防ぐこと。
- **非同期処理と多重実行防止**
  - ボタン連打・演出中・通信待機中の二重実行、スキル重複発動、報酬二重付与を `GameState.isProcessing` 等のガードで防止すること。
  - レーン・対象選択（`waitPlayerLaneSelection` 等）中の競合を防ぎ、キャンセル・早期 `return`・例外発生時も `try...finally` 等で処理中フラグや一時選択モード（`isPlacementMode`, `isDiscardingMode` 等）を確実に復旧させ操作不能を残さないこと。
- **定数管理と過剰なリファクタリングの防止**
  - 定数を利用し、マジックナンバーを使わないこと。
  - 共通処理はまとめてDRY原則を保つこと。ただしDRY原則の過剰適用を禁止し、仕様上意味が異なる処理（特に「召喚」と「配置」）を曖昧なフラグで無理に統合したり不要な抽象化を行わないこと。共通化する場合も仕様上の違いが明確に表現される設計を優先すること。
- **セーブデータ保護・後方互換性とPHP API安全性**
  - LocalStorageのユーザデータや、サーバ上のユーザデータとの不整合は絶対発生させないこと。（ユーザのデータの消失は最も注意すること）
  - 古いセーブデータ・旧カードID（`CARD_ID_MIGRATION_MAP`）・旧デッキ形式（文字列配列と `{ id, isPremium, isShine }` 混在）の互換性を維持し、パース失敗・不正値への安全なフォールバックを行い、保存失敗や破損検知時に初期値で既存データを上書き消去しないこと。
  - PHP API（フラットファイルJSON永続化）では、入力値の型・範囲・マスタ許可値検証とUUID等の正規表現サニタイズを行い、更新時は排他ロック（`modifyPlayerDataWithLock` / `LOCK_EX`）＋一時ファイル＆`rename` アトミック保存を用い、`status === 'corrupted'` 時の初期値上書きを禁止する。`match_id` / `used_serials` による二重実行防止、内部情報を漏洩しないエラー応答、レスポンス互換性を維持すること。
- 【絶対厳守】変更・新規作成したすべてのファイルについて、インポート漏れや未定義の変数（`no-undef` など）が絶対に発生していないか、コミットや報告の前に必ず `npm run format` や `eslint`（`npm run lint` ※`npm run format` は画像WebP変換・サムネイル生成・音声圧縮を含むため作業中アセットがある場合は対象単位の Prettier と `npm run lint` を使い分ける）を実行して二重チェック・検証すること。
  - **【先走りの絶対禁止】コード変更後は、必ず `npm run build` や `eslint` 等の検証ツールを実行し、その実行結果（エラーゼロ・100%成功）を自分の目で受信・確認するまで、決してユーザーへ「修正完了」などの報告テキストを先走って出力・送信してはならない。**
- 【絶対厳守】すべての関数へのドキュメント（JSDoc等）記載とシステム処理コメント記述の徹底
  - 新規作成・変更・追加するすべての関数（ヘルパー、コンポーネント、ユーティリティ問わず）に、概要・目的・引数（`@param`）・戻り値（`@return`）を明記した日本語JSDocを**例外なく必ず記載すること**。
  - ゲームのシステムやバトルロジックに関わる処理は、挙動・意図・副作用・境界条件が一目で理解できるよう具体的な日本語解説コメントを記載すること（自明な処理を繰り返すだけの低価値コメントは避け、実装変更時は既存コメント・ドキュメントも同時更新して乖離を防ぐこと）。
- 【絶対厳守】オブジェクトプロパティ・関数戻り値の構造変更時における呼び出し元影響調査の徹底
  - 関数の引数・戻り値やオブジェクトのプロパティを削除・置換・再構築する際、局所的な差分や外部指摘（CodeRabbit等）のみに視野狭窄して作業してはならない。
  - **必ず事前に対象オブジェクト/関数の全呼び出し元を `grep` 検索で実地調査し、呼び出し側システム（対戦画面、モーダル、UI、AI、API等）が要求しているプロパティ（例: `hp`, `playmat`, `color` 等）が欠落・消失しないことを100%検証してからコード変更に着手すること。**
  - セーブデータ（`savedConfig` 等）とマスタデータをマージする際は、既存の追加属性消失を防ぐため既存オブジェクトを先頭に展開し、計算・正規化済みのプロパティを後続で上書き補正する順序を守ること。
- 【絶対厳守】報酬付与・カードドロップ・解放処理等の重要判定における「ホワイトリスト（許可制）方式」の徹底
  - ゲームモードや条件ごとの報酬付与、カードドロップ、機能解放などの判定で、対象外を否定条件で列挙する「ブラックリスト（除外判定）方式（`mode !== 'a' && mode !== 'b' && ...`）」を**絶対に禁止する**。
  - 新モード追加時のすり抜け事故を恒久的に防ぐため、必ず許可対象のみを明示判定するホワイトリスト関数（例: `checkIsCardDropEligible(gameMode)` 等）を使用・定義すること。
- 【絶対厳守】AI思考・シミュレーションにおける「空きレーン優先・決め打ちヒューリスティック」の絶対禁止
  - AI思考ルーチン、直前シミュレーション、シミュレーションエンジン（`engine.js`, `ai_normal.js` 等）において、「空きレーンがあれば優先する」「空きがないから固定レーンを上書きする」といった**安直な空き枠優先ヒューリスティックや決め打ちハードコード（例: `const emptyLanes = ...; if (emptyLanes.length > 0) targetLane = emptyLanes[0]; else targetLane = validOccupiedLanes[0];`）を絶対に禁止する**。
  - トークン配置、使役、奇襲、分身、復活、傀儡、リーダースキル等、カードを場に置くあらゆるシミュレーションで、「空きレーンへの配置」も「既存カード上書き配置」も**等しく正当な候補レーン**として扱い、各候補レーンの評価関数（`evaluateTurnOutcome` 等）スコアを比較して最善手を選択すること。フォールバック時も最弱カード・トークン上書き等の合理的な選択ロジックを用いること。
- 【絶対厳守】AIシミュレーション・評価における「上書きペナルティ（自壊ペナルティ）」の絶対禁止
  - AIのあらゆる評価処理において、**「味方カードを上書きしたから減点する」（例: `score -= lostPower * 1000` 等）といった人為的な上書きペナルティ（自壊ペナルティ）の付与を完全に禁止する**。
  - AI思考は、盤面に配置・召喚した後の完全な戦闘シミュレーション（`advanceCombatPhase` 等）および客観的な盤面総合評価関数（`evaluateTurnOutcome` / `evaluateSimState`）によってのみ判断すること。
- 【絶対厳守】UI・モーダルにおける「ぼかし（blur）」の絶対禁止とCSS・操作性基準
  - 端末の描画パフォーマンス維持およびデザイン統一のため、UI要素や背景への「ぼかし（`backdrop-filter: blur`, `filter: blur` 等）」の使用を**完全に禁止する**（特定バトルVFXキーフレームを除く）。モーダル背景には共通クラス（`.modal-overlay`）と純粋な透過色（`rgba(0, 0, 0, 0.85)` 等）を使用すること。
  - モバイル表示崩れを防ぐため、画面高さ指定には単独の `100vh` 等を使用せず `dvh` / `svh` を基本とすること（旧環境向けフォールバック併記や `min()` 内の補助指定は許容）。ボタンの操作可能状態（`disabled` 付与時の `:disabled` スタイル定義を含む）の明示、インラインスタイルからCSSクラスへ移行する際の既存親セレクタ詳細度との競合確認、モーダルのフォーカス・キーボード操作配慮、`transform` / `opacity` 優先のアニメーションを守ること。

# Game Rules

- デッキ枚数は20枚。
- LocalStorageにユーザデータを保存する。
- API経由でサーバに防衛戦のデッキやポイントを保存する。

## ゲーム状態の不変条件と特殊状態の保護

- **不変条件:** リーダーHP・SPの整合性、盤面3レーン構造、山札トップ規約（配列末尾 `deck.pop()` を山札トップとして統一し `shift()` を混入させないこと）、マスタ定数（`CARD_MASTER`, `CHARACTERS`, `LEADER_SKILLS`, `SKILLS`）の非汚染を維持すること。手札・山札・墓地・盤面間のカード移動で意図しない消失や同一参照の重複を起こさず（検索は参照一致・`uid` 一致を優先し `isPremium` / `isShine` 等の個体属性を保持）、選択キャンセル・拒否・例外時は元のゾーン・山札位置へ正確に復元すること。バトル処理の変更時は実戦ロジック（`src/game/`）と汎用エンジン（`src/game/engine/`）・AI思考（`src/game/ai_normal.js`）の挙動対称性を保つこと。
- **特殊状態の保護:** トークンの墓地送り時消滅、装備・合体・起動による統合・身代わり、および**スキル解決中（`isSkillResolving`）または解決中スキルから生成されたカード（`skillResolvingOwner`）が未被弾（`hasTakenDamage !== true`）の間はパワー0でも一連の解決完了まで盤面に残る仕様**を保護し、解決途中で誤って早期破壊しないこと。

## 【絶対厳守ルール】「召喚」と「配置」の厳密な区別

カードを場に出す処理を実装する際、以下の2種類のアクションを「絶対に」混同せず、分離して実装すること。

1. **「召喚（Summon）」**
   - **定義:** 手札からのプレイ、または制約ルール（伝説・生贄・挑戦・頂点・降臨・先攻初手中央制限）を満たしてカードを場に出すメインアクション。召喚時のオンプレイ能力が発動する。
   - **該当アクション・スキル一覧 (内部ID):**
     - **手札プレイ:** 手札からのカード通常召喚（メイン操作）
     - **「召喚」スキル:** `summon`（手札からの召喚、旧名: 詠唱 / `chant` を統合）
     - **「召集」スキル:** `assemble`（デッキからの召喚）
     - **「号令」スキル:** `call`（デッキトップからの召喚）
     - **「鍛造」スキル:** `forge`
     - **「狂気」スキル:** `madness`（手札から捨てられた時の召喚）
     - **「反魂」スキル:** `reanimate`（デッキから墓地に送られた時の召喚）
     - **「招来」スキル:** `invoke`（手札・場のカードを捨てて手札または山札から召喚）
     - **「誘発」スキル:** `trigger`（相手召喚時の手札からの割り込み召喚）
     - **リーダースキル「試練の宮殿」:** `dungeon_summon_leader`
     - **リーダースキル「次元斬」:** `daemon_call`
     - **リーダースキル「万魔の招来」:** `demonic_call`
   - **制約チェック:** **【あり（有効）】** (`checkConstraints = true`)
   - **実装基準:** レーン選択では `waitPlayerLaneSelection(..., checkConstraints = true)` を使用し、配置確定後に `resolveOnPlaySkill(...)` を呼び出して召喚時オンプレイ能力を発動する。
   - **挙動:** 「伝説（`legendary`: 中央のみ）」「生贄（`takeover`: 配置済みレーンのみ）」「挑戦（`challenge`: 正面に敵がいるレーン）」「頂点（`apex`: 自分の「伝説」カードが配置されているレーンのみ）」などの配置制約ルールに**必ず従わなければならない**。また「降臨（`advent`）」を持つカードは能力以外（通常の手札プレイ）では召喚できない。
   - **画面ボタン表記:** 「召喚を完了」（キャンセル可能時は「召喚完了」／「キャンセル」）

2. **「配置（Place）」**
   - **定義:** スキル効果やリーダースキルによって、カードやトークンを制約ルールを無視して場に直接置く特殊アクション。原則として召喚時スキルは発動しない。
   - **該当アクション・スキル一覧 (内部ID):**
     - **「復活」スキル:** `resurrect`（自分の墓地からの配置）
     - **「傀儡」スキル:** `puppet`（相手の墓地からの配置）
     - **「分身」スキル:** `clone`（隣接レーンへの分身トークン配置）
     - **「使役」スキル:** `servant`（トークン配置）
     - **「奇襲」スキル:** `ambush`（トークン配置後に即攻撃）
     - **リーダースキル「竜王の降臨」:** `dragon_summon`
     - **リーダースキル「焦熱のプレリュード」:** `dragon_high_ritual`
     - **リーダースキル「魔王の化身」:** `satan_avatar`
     - **リーダースキル「聖なる進軍」:** `holy_march`
     - **リーダースキル「暗黒の軍勢」:** `evil_march`
     - **リーダースキル「死の標的」:** `death_target`
     - **リーダースキル「棺の解放」:** `devilhunter_resurrect`
     - **リーダースキル「オーバードライブ」:** `overdrive`
     - **リーダースキル「魔宴の儀」:** `warlock_place_daemons`
     - **リーダースキル「鉄の行進」:** `iron_march`
     - **リーダースキル「ラスト・バタリオン」:** `last_battalion`
     - **リーダースキル「百鬼夜行」:** `night_parade`
     - **リーダースキル「連携攻撃」:** `elf_polarbear_combo`
   - **制約チェック:** **【なし（無視）】** (`checkConstraints = false`)
   - **実装基準:** レーン選択では `waitPlayerLaneSelection(..., checkConstraints = false)` を使用し、`resolveOnPlaySkill(...)` を呼び出さない（オンプレイ能力を抑止する）。
   - **挙動:** 対象カードが「伝説」や「生贄」などの制約ルールを持っていたとしても、**封印レーンを除く任意のレーンに置くことができる**。
   - **画面ボタン表記:** 「配置を完了」（または「配置完了」）

※ 重要例外: 「封印（`seal`）」されたレーンに関しては、レーン選択時（`waitPlayerLaneSelection`）と配置確定時（`playCard` 等）の両方の段階で、上記1および2のどちらの手段（召喚・配置・移動）であっても**強制的に拒否・ブロックされ、配置することができない**。これは最優先のグローバルルールである。

## 【絶対厳守ルール】日本語スキル名の英語IDへの変換

日本語の「スキル名」を内部の英語IDに変換・解釈する際、**絶対に推測や類似の単語で代用せず、`src/utils/constants/skills.js` に基づいて厳密に一致させること**。特に以下の取り違えを厳禁とする：

- 「変身」＝ `metamorph`（絶対に `morph` や `transform` としないこと）
- 「変化」＝ `morph`
- 「号令」＝ `call`
- 「狂気」＝ `madness`
- 「忘却」＝ `silence`（正面のカードの全能力無効）
- 「沈黙」＝ `oblivion`（お互いの場の全カードの全能力無効）

スキルの修正・評価時は必ず `src/utils/constants/skills.js` で日本語名（`name`）と英語キー（ID）を確認してから着手すること。

## 【絶対厳守ルール】日本語リーダースキル名の英語IDへの変換

リーダースキル名を内部の英語ID（`action`）に変換する際、**推測や類似単語での代用を禁止し、`src/utils/constants/characters.js` および `src/utils/constants/leaderSkills.js` の定義に基づいて厳密に一致させること**。

- 英語IDは `LEADER_SKILLS[key].action` / `CHARACTERS[key].leaderSkill.action`（例: `annihilation`, `devilhunter_resurrect`, `death_target`）、日本語名は `name`（例: `殲滅光線`, `棺の解放`, `死の標的`）である。キャラクター名・スキン条件とリーダースキル名の両方を照合して確認すること。

## 【絶対厳守ルール】日本語カード名の英語IDへの変換

カード名を内部の英語ID（`id`）に変換する際、**部分一致や推測を禁止し、`src/utils/constants/cards.js` の `CARD_MASTER` 配列（`id` と `name`、例: `golem`＝`大理石のゴーレム`, `clone`＝`鏡の戦士`）に基づいて完全一致で厳密に照合すること**。
